# Reference Repositories

Five external projects studied for Asteria (list: [must_read_repo.txt](must_read_repo.txt)). Each was read
from source at a pinned commit, and key claims were spot-checked by hand. **No code is copied.** These are
references for ideas and for mistakes to avoid.

| Repo | One-line verdict | Review |
|---|---|---|
| VirtualConsole | Shows the whole territory (ISA → assembler → compiler → shell), but the "OS" is host services and there is no timing or traps | [virtualconsole.md](virtualconsole.md) |
| LC-John RISCV-Simulator | Three CPU modes, never cross-checked, and they disagree. A catalogue of pipeline bugs Asteria's design prevents | [riscv-simulator-lcjohn.md](riscv-simulator-lcjohn.md) |
| MARSS-RISCV | Rich full-system machinery, but timing is bolted onto an emulator: synchronous latency, one DRAM request at a time, one clock | [marss-riscv.md](marss-riscv.md) |
| Siliscope | **Claims verified as real.** xv6-class OS + passive analyzer on RISC-V. **Closest competitor**, which sharpens Asteria's positioning | [siliscope.md](siliscope.md) |
| gem5 | Independently confirms Asteria's core decisions and contributes six concrete improvements | [gem5.md](gem5.md) |

## What the reviews confirmed
Several Asteria decisions are validated by *other projects' failures*:
- **D10 (evaluate → commit):** both pipelines that order stage evaluation in reverse (MARSS, LC-John) have
  order-dependent behaviour. LC-John has real bugs from it. gem5 needs reverse order *only* for zero-delay
  backward signals.
- **D8 + D7 (fair three-CPU comparison):** LC-John's comparison is meaningless: only one model sees cache
  latency, there is no clock period, and nanoseconds are used as cycles.
- **One ISA definition + differential fuzzer:** LC-John's models disagree on semantics. MARSS has two decoders.
- **D9 (clock domains):** MARSS counts DRAM cycles as CPU cycles. gem5 uses a 64-bit tick with strong cycle types,
  as we do.
- **D14 (determinism):** MARSS uses unseeded `rand()`. VirtualConsole uses a wall-clock keyboard.
- **Real traps (spec §5):** VirtualConsole halts silently on bad opcodes and reads 0 from unmapped memory.

## Milestone-level techniques collected (no decision change needed)
- **M1:** structured diagnostics `{file, line, column, message}`; assembler records symbol-derived operands (cheap relocations).
- **M4:** generic mispredict check (EX next-PC ≠ ID's PC); stall/bubble bit vectors; instruction-latch pool; in-order
  completion queue for MUL/DIV; configurable branch-resolution stage; unit tests pinning exact cycle counts.
- **M5:** five-method replacement-policy interface; LRU by per-set counter; tag vs data latency and sequential/parallel access knob.
- **M6:** fixed-latency + row-hit-discount baseline model; write-drain watermarks; page-policy enum.
- **M8:** generate device constants (C header + asm `.equ`) from one memory-map table; separate tick list from address map.
- **M10:** precedence-level parser, declaration pre-pass, constant folding, result-in-one-register codegen, ABI frames from day one.
- **M11:** crash tester with no-journal control build; Belady check gated per policy; memory balloon; `SCRATCH == 0`
  trap trick; stack canaries; `copyout` breaks COW; MLFQ table.

## Positioning
Siliscope shows that an xv6-class OS plus a performance analyzer on RISC-V **already exists** as a portfolio
project. Asteria's distinctive claims are therefore:
1. an **original ISA** with its own toolchain;
2. **three real cycle-level CPUs whose timing changes OS behaviour** (Siliscope's analyzer is passive);
3. a **DRAM controller with bank state machines in its own clock domain**, checked by an independent timing checker;
4. the **Studio**, where every cycle is visible and can be stepped backwards.

The README and resume should lead with these.
